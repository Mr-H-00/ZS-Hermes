# 知识库路径型目录实体化

状态：proposed
类型：feature
Owner：backend/package/yuxi/knowledge/utils/kb_utils.py

## 问题

目录上传和部分外部导入通过 `source_path` 把相对路径保存到文件记录的 `filename`。文件列表按路径分段动态投影虚拟文件夹，因此可以保留目录层级，却没有独立文件夹记录、稳定 `file_id`、创建人和创建时间，也不能安全使用真实文件夹的移动与重命名能力。

文件夹管理已经以真实 `knowledge_files` 记录和 `parent_id` 关系作为可写目录模型。新的可写知识库目录上传继续产生虚拟文件夹，会让相同用户操作得到两种能力不同但视觉相同的目录。列表查询时静默创建真实目录又会让读取产生批量持久化副作用，并在分页、重试和并发读取下产生不可预测结果。

## 提案

可写且支持文档的知识库在接收带 `source_paths` 的目录上传时实体化目录层级。用例从规范化后的相对路径提取目录段，按父子顺序幂等取得或创建真实文件夹记录，并把文件记录保存为叶子文件名和对应真实 `parent_id`。真实文件夹记录保存执行上传的 `created_by` 和服务端创建时间。普通多文件上传没有目录相对路径时继续写入当前目标文件夹，不额外创建目录。

目录实体化属于写用例，不属于列表 repository。HTTP 路由只完成请求和权限适配；用例流程进入 `yuxi.services`，目录与文件的查询、精确字段更新和事务锁进入 repository。目录创建与文件归属更新按同一知识库目录树锁串行化；同一父目录下的同名真实文件夹必须幂等复用或明确冲突，不能创建平行重复目录。批量上传继续允许文件级部分成功，但每个成功文件的目录链和文件归属必须原子发布，失败不能留下该文件对应的半条目录关系。

已有虚拟文件夹不在列表读取时自动迁移。可写文档知识库提供显式“转换为真实文件夹”操作：请求携带当前真实 `parent_id` 和规范化 `path_prefix`，服务端预览受影响文件数与冲突后，由管理者确认执行。转换在单一事务和目录树锁内创建目标真实文件夹，把严格匹配该路径段的直属文件及剩余相对路径迁入新 `parent_id`，并从 `filename` 去掉已实体化的一个路径段。嵌套剩余路径可以继续作为虚拟目录，或由后续显式操作逐层实体化。

只读 Connector 保持虚拟路径投影且拒绝实体化。MinIO 对象 URL、文件 `file_id`、解析 Markdown 和向量身份不因目录实体化而移动；实现前必须确认所有按文件名冗余保存的 Chunk、知识导图和其他派生数据 Owner。依赖展示名的派生状态在同一用例中精确更新或明确标记为待刷新，不能静默保留相互矛盾的名称。

前端对目录上传结果展示真实文件夹。虚拟文件夹的操作菜单只为具备管理权限且后端声明支持实体化的知识库显示“转换为真实文件夹”；操作前展示影响文件数量、目标位置、名称冲突和不可撤销影响。转换成功后重新读取服务端目录，不使用乐观树结构代替持久化事实。

## 替代方案

- 继续只使用虚拟文件夹：导入最简单且适合只读外部数据，但可写知识库会长期存在两套外观相同、能力不同的目录模型。
- 在列表查询时自动转换：调用方无需显式操作，但读取会批量写数据库，分页、缓存、失败重试和权限语义都难以预测，因此拒绝。
- 上传完成后把整批文件放进一个后台迁移任务：适合超大批次，但会长期暴露“上传完成、目录尚未实体化”的中间态；首期优先让每个成功文件的目录关系原子发布，超过验证规模阈值后再单独评估后台任务。
- 转换虚拟文件夹时递归实体化全部后代：一次得到完整真实树，但事务范围和冲突面会随目录规模快速扩大；首期只实体化一个路径段。
- 移动 MinIO 对象以匹配展示目录：对象身份目前不由展示目录拥有，迁移会增加无必要的外部副作用，因此拒绝。

## 风险

路径规范化、同级名称冲突和并发创建会直接影响持久目录树。实现需要真实 PostgreSQL 事务与确定性并发负控，不能用 mock 调用次数替代。现有 `knowledge_files` 没有表达同级文件夹名称唯一性的专用数据约束；提案落地前必须决定并验证大小写规则、文件与文件夹是否共享名称空间，以及 schema 演进对历史重复目录的处理。

历史虚拟目录可能包含大量文件。显式转换接口必须先计算影响规模并设置同步执行上限；超过上限时明确拒绝并报告后续方案，不能在 HTTP 请求中无界批量更新，也不能静默切换到不可恢复的进程内后台任务。

从完整相对路径改为 `parent_id + 叶子名称` 会改变展示名事实。文件内容、对象和向量以 `file_id` 为身份的主张需要由实际回读证明；任何仍以旧文件名作为身份或引用的 consumer 都必须在实现前纳入同一事务、失效流程或明确排除实体化能力。
