# 按文件查看和构建知识图谱

状态：implemented
类型：feature
Owner：backend/yuxi/modules/knowledge/graphs/service.py

## 问题

知识库图谱需要按单个文件查看和构建。实体可能由多个文件共享，单按实体筛选会引入其他文件的关系和属性；全库待构建计数也不能表示单个文件的状态。

## 决策

### 实现方案

图谱查询接受可选单个文件 ID，由知识库读取权限和图谱服务校验文件归属。图谱 repository 读取文件当前可见代次的实体、关系及分块来源；服务按来源查询 Neo4j，保留孤立实体和符合查询条件的分块，排除其他来源的关系和属性。文件代次及投影读取使用现有锁边界协调。

图谱索引提交接受可选文件 ID；不指定文件时保留全库增量构建，显式提供无效文件 ID 时拒绝请求。构建服务校验文件和当前分块，将文件 ID 与代次保存到持久作业，继续使用知识库级任务互斥。worker 持有投影锁与文件行锁，校验代次，并按目标文件处理可见分块及相关实体、关系向量；目标文件关联的失败向量可重试，共享记录按来源纳入，其他文件独有的记录不受影响。

图谱页面通过路由保存单文件范围，提供搜索、选择与清除；文件菜单直接进入该范围，页面显示结果、空状态或查询错误。构建服务读取文件当前可见代次中尚未完成图谱索引的分块数，页面在选择文件或任务结束后回读，仅在有待构建分块时展示文件构建操作；加载失败可重试，旧文件的迟到结果不覆盖当前选择。任务状态串行轮询，终态后刷新图谱。知识库管理面板标注全库范围，文件抽取与向量构建使用知识库已锁定的配置，只读用户不能提交构建。

## 替代方案

文件列表维护图谱状态会增加查询及状态同步成本；直接进入图谱页面也允许用户为空文件启动构建。仅按实体两端筛选关系会引入其他文件的数据；已有图谱或全库计数不能证明单个文件所有分块已完成，而单独维护文件完成标志会复制分块状态。

继续只提供全库构建无法满足单文件操作；仅限制抽取分块但保留全库向量和失败判定会处理其他文件或错误报告目标任务。独立作业体系会复制现有互斥、恢复与状态所有权。

## 后果

文件图谱查询跨 PostgreSQL 和 Neo4j，需协调文件代次与投影清理；大文件的来源集合会传给图数据库，结果仍受图谱查询上限约束。共享实体或关系的向量可能同时服务多个文件，目标文件构建会处理其关联的共享记录。

结构已完成但向量尚未完成的分块仍属于待构建范围，失败后可重试。文件行锁在构建期间阻止代次切换；构建与既有全库流程一样需要后台数据库连接池具备查询余量，过小的自定义连接池可能超时。

## 验证

真实 PostgreSQL 和 Neo4j 测试覆盖文件、代次、关系来源、共享实体、失败向量重试及代次锁；真实 HTTP 测试覆盖提交校验、文件归属、目录和待完成向量。前端测试覆盖直接进入文件图谱、单选、空结果、构建入口、状态轮询、失败重试及图谱刷新，浏览器组件页面验证状态失败后的重试。

未索引文件的真实模型和 Milvus 跨进程构建未验证；图谱处理链路使用确定性替身验证。
