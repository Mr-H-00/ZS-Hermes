# 本地前端页面加载

状态：implemented
类型：architecture
Owner：docker-compose.frontend-static.yml

## 问题

本地开发服务器同时转换源码、监听文件和代理 API。仅需使用应用时，这些工作会占用页面导航所需的资源。首次打开网盘时，未选中的子页也会进入加载链路。

## 决策

### 实现方案

本地静态前端覆盖文件复用生产目标和 Nginx 代理配置。它替换前端镜像、命令、源码挂载和容器内监听端口，保留宿主机 Web 端口和既有服务网络。使用步骤由[快速开始](../../../intro/quick-start.md#本地使用静态前端)维护。

网盘在选中「我的成果」或「我的云盘」时加载对应组件，复用异步面板的加载与失败反馈，并沿用已有的子页缓存和查询参数处理。会话布局和消息渲染同步装配，以维持最大化面板的传送目标和历史消息的滚动定位。

## 替代方案

将整个本地环境替换为生产 Compose 需要调整后端配置和服务拓扑。统一预取侧栏路由会让未访问页面与当前页面竞争下载。将整个文件面板或回答组件改成异步会推迟传送目标的创建或改变历史消息的测量时序。

## 后果

静态入口以构建产物启动。前端更新需要重新构建，开发时可切回原有的热更新入口。API 或 MinIO 重新创建时重启静态前端即可刷新 Nginx 的上游解析。网盘子页的首次打开包含其模块加载时间。

## 验证

使用 Edge 在同一台主机交替访问 Vite 与静态前端，对比从「去对话」点击到对话页可见的时间，以及网盘、扩展、API 服务和数据总览的首次打开时间。使用模拟 API 固定浏览器测量的业务输入。

`frontend/test/browser/navigationPanelLoading.js` 观察首次打开网盘时的模块请求，并通过真实页面点击验证网盘预览、网盘子页、历史答复和会话侧栏。还通过实际容器验证首页、会话深链、同源 API 就绪检查和本地 PDF CMap 资源。
