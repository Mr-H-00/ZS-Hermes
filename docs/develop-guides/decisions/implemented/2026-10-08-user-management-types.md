# 用户管理按身份类型分页与展示来源

状态：implemented
类型：bug-fix
Owner：backend/yuxi/modules/identity/repositories/users.py

## 问题

APP 终端用户与系统账号共用 users 表。用户管理列表混入自动创建的长 ID，使系统账号难以查找，并挤压角色与来源列。终端用户没有部门，但其 APP 来源可以从持久身份读取。

## 决策

用户管理默认显示系统用户，允许切换到 APP 终端用户或全部类型。类型由 user_kind 决定，名称和 ID 前缀不参与类型判断。来源列对系统用户展示部门，对 APP 终端用户展示 app_id；系统没有独立的 APP 名称实体。

### 实现方案

分页 HTTP 入口接受 human、end_user、all，默认 human，并把 all 转为无类型限制；身份服务保留管理员部门可见范围，repository 在计数和分页前应用同一筛选。管理分页响应包含 user_kind 和 app_id，其他账号响应契约保持原有字段。

前端 API 传递用户类型，切换筛选回到第一页。列表采用固定列布局，长用户名、ID 与来源单行省略，角色保持单行；用户信息按钮通过点击和键盘打开完整用户名、ID 与 APP 实例值。

## 替代方案

在前端过滤当前页会造成页数和总数错误；按 endusr_ 前缀隐藏会误伤名称相似的系统用户。用 API Key 名称充当 APP 名称会混淆凭据和身份，同一 APP 可以对应多个 Key，因此直接展示身份 app_id。

## 后果

管理分页接口未传类型时只返回系统用户；要读取所有类型的调用方显式传 all。无需修改 Schema 或既有用户数据。部门管理员的原有可见范围继续生效，类型筛选不扩大权限。APP 终端用户的编辑入口禁用，继续使用查看与删除；产品账号表单的角色和部门字段只服务系统用户。

## 验证

Repository 回归用例用系统用户的 endusr_ 前缀与 APP 用户同时证明类型过滤、分页和总数。真实 HTTP/PostgreSQL 测试从 Public API 创建终端用户，核对默认隐藏、显式类型显示、来源字段和非法类型拒绝。前端单测验证默认请求、切换类型回到第一页和搜索条件保留；真实页面检查完整信息查看、长文本、角色与来源列及浅暗主题和窄屏布局。

终端用户编辑回归执行真实组件 setup，核对 end_user 无法打开产品编辑表单，human 仍可进入。移除类型限制后同一断言失败，恢复后通过。浏览器使用固定账号数据装配提交快照组件，回读编辑按钮 disabled 状态与系统用户表单；该组件检查不代替真实 HTTP。
