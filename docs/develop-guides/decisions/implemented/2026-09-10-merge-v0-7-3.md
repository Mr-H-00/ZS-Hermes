# 合并 v0.7.3 并保留定制能力

状态：implemented
类型：architecture
Owner：ARCHITECTURE.md

本记录取代 2026-09-03 的[取消 LITE 运行模式](../archived/2026-09-03-remove-lite-mode.md)决定；后者只保留历史背景。

## 问题

当前分支基于 `v0.7.2`，包含父子知识块、稀疏/稠密向量、加权融合、RRF、BGE-M3 和 Chunks 统计等定制开发；官方 `v0.7.3` 同时引入了 AgentRun、FIFO、lease、checkpoint、恢复和 Durable Task 等运行时变化。直接覆盖 `Yuxi-0.7.3/` 会丢失定制实现，继续停留在 `v0.7.2` 又会遗漏上游修复。LITE 仍是本地部署契约，不能因上游历史决定而被静默删除。

## 决策

以 `v0.7.2` 为共同祖先对当前分支与官方 `v0.7.3` 做三方合并。无冲突的上游变化全部保留；冲突处以 `v0.7.3` 的接口、生命周期和依赖装配为结构基线，再把仍有真实入口、测试和数据契约的定制能力移植到各自语义 Owner。知识库行为由 `yuxi.knowledge` 与其 repository/provider 拥有；`yuxi.config.runtime` 拥有 LITE 解析和知识能力开关；Compose 拥有 API、worker、迁移器的环境传播、端口与服务拓扑；API/worker/迁移器启动边界分别由 lifespan、`yuxi.services.run_worker` 和 `yuxi.storage_migration` 拥有；`backend/server/routers` 拥有路由注册与 discovery 协议，Web runtime store 和 CLI discovery consumer 只消费该协议。

知识库重新解析与索引只经过 `parse_file`、`index_file` 和 `reslice_file`，不恢复无生产消费者且绕过状态 CAS、processing owner 与 Parent-Child 提交语义的 `update_content` 旁路。Task 驱动的解析和索引只接受成对的 `processing_task_id` 与 `processing_owner`，解析参数与 `parsing` 状态及 owner 在同一次 claim 中写入；Parent-Child 入库缺少 owner 时在认领文件前失败。解析和索引按 `(kb_id, file_id)` 持有 PostgreSQL transaction advisory lock，状态认领与 MinIO、Milvus、Neo4j 外部副作用对同一文件串行；同步线程写入完成后才传播取消，普通异步解析仍立即响应取消。版本激活按 `TaskRecord -> KnowledgeFile -> KnowledgeDocumentVersion` 锁序执行，并在同一 Task-owned transaction 内切换 active 版本、发布文件 `indexed` 终态与统计、清除 owner，提交前 lease 失效或文件 owner 切换会整体回滚 PostgreSQL 事实。Parent-Child 查询以 PostgreSQL active version 持久化的 embedding 维度选择已有 Milvus collection；active version 维度混合或 provider 返回的查询向量维度不匹配时，在访问 Milvus collection 前失败。

`knowledge_parent_child_cleanup` 仅对 `RuntimeError` 重试，最多三次总尝试且包含首次 claim。重新入队必须由仍持有 owner 且 lease 未过期的 attempt 在行锁内完成；owner 丢失或 lease 过期不重新入队，已请求取消优先收敛为 `cancelled`。前两次失败保留原始去重意图和首次开始时间、清空上一 attempt 的执行投影；第三次失败继续走既有 failure hook 并终态为 `failed`。不引入通用重试调度、退避或公开配置面，因此连续失败会快速耗尽预算。

保留 LITE：该模式继续装配认证、Agent/聊天/AgentRun、用户定时 Agent、非知识类 Skills、MCP、模型、Project/Workspace/Viewer 和系统管理能力；同时跳过 knowledge schema、知识 Durable Task consumer 与 reconciliation、知识路由、知识域 Dashboard、评估、图谱连接以及 `knowledge-base` Skill/工具，并在 discovery 中关闭 Web 与 CLI 的知识能力声明。完整模式继续使用 `v0.7.3` 的全部知识链路。附件 parser 在两种模式都只在真实解析动作发生时惰性加载。合并不修改本地 `.env`、运行数据或 `Yuxi-0.7.3/` 参考目录。

## 替代方案

- 用 `Yuxi-0.7.3/` 覆盖工作树：无法可靠识别同名文件中的定制语义，会破坏已有开发。
- 将定制提交 rebase 或逐个 cherry-pick 到 `v0.7.3`：会重写已经包含 `v0.7.2` 融合工作的历史并重复解决同一批冲突。
- 继续停留在 `v0.7.2`：不能满足升级目标，也会遗漏 `v0.7.3` 的安全和运行修复。
- 跟随上游删除 LITE：会破坏已交付的轻量部署契约，并强制现有部署新增完整知识基础设施；不采用。

## 后果

最终提交同时包含两条父系；新版 AgentRun/FIFO/lease/checkpoint/Durable Task 作为运行时基线，定制检索和统计能力继续由原有入口提供。Compose 默认宿主机端口保持本地约定（MinIO `19000/19001`、Redis `16379`），`.env` 和已有持久化数据保持不变。LITE 与完整模式继续是同一版本的两种明确装配路径，新增或删除任一模式能力都必须同时更新其 Owner、负向测试和决策记录。

同一文件的解析和索引等待当前同步外部写真正结束后才释放处理锁；取消延迟只覆盖该不可中断调用，不覆盖整个 workflow。不同文件继续并行，外部删除失败时 PostgreSQL 引用保留给后续重试。Milvus 和图谱投影的每个破坏性清理阶段都再次验证当前文件 processing owner，旧 attempt 即使在先前阶段仍有效，也不能删除 successor 已写入的投影。
